Regarding Bunker:

Right now the problem is that:
 - i rethought Event/Reply models and refactored Agent accordingly.
 - there are new fields, new structure.
 - Bunker is really, really outdated. It doesn't really do anything with new information, just takes what's needed to the caller and returns.

So, what is there to do:
 - probably a new model of ProcessedReply - to return just what's needed?
 - really handle (or just make a pattern for when a db will be there) new fields, such as datetime and others.

 That's all there is for this feat/refactor.

In future I could make Call better by adding what payload structure/variables bot actually waits for. This way Bunker will be able to compare what agent returned and what's actually used/not used.
This is possible with Call, or with DB. I mean, I could do both at the same time. In DB there would be actual fields that Bunker has seen; in Call - that Bot expects.

I somehow find the Call idea better, even though it makes the contracts more complex and heavier. Probably gonna go with the db idea.. Idk. Both options are valid.

Cuz when I inevitably change services and their output payload, I would have to go to the bot and change the expected key also. With db is more easy - changes are automatically updated on run.

But to be honest, "i want this action from this service, I expect these keys" makes more sense for me than storing the thing in database.
And db-way doesn't really do much, only make it a bunker-level check. If bot needs these keys, what can Bunker do when there's no such keys from the service? Nothing (in YAGNI limits).

But it's a cool thing, I mean. Bunker will be able to track new services, their actions and stuff. Not useful, but seems good.
